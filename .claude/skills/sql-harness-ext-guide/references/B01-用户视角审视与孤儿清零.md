# B01 — 用户视角审视与孤儿清零

> **本 ref 解决的不是"怎么加",而是"该不该加 / 该不该留"。**
> A02 扩展方法讲"怎么加",本 ref 讲"加之前先判必要性,加完之后判是否还有用户可见路径"。A01 目录规范讲"放对位置",本 ref 讲"该不该存在"。

---

## 1. 为什么需要这道闸口

sql-harness 是**单进程 CLI + agent 运行时工具**,代码与最终用户之间隔了三层:

```
源码树 ──(uv build)──> wheel ──(uv tool install)──> 用户 venv ──(sql-harness skill install)──> agent 运行时
                                              │
                                              └─(BH_SQL_HOME)──> ~/.config/sql-harness/  ← 用户可写区
```

**任何一层断链,前面的代码对用户就是零。** 仓库里"看起来存在"的文件:

- 不在 `pyproject.toml` 的 `force-include` → wheel 不带 → 用户装完没这个文件
- `init` / `skill install` 没复制逻辑 → 即使 wheel 带了也不会落到用户目录
- loader 不识别文件名 → 即使用户目录存在也不被加载
- 文档里写了但代码不实现 → 用户照着做报错
- 文档里写了但文档自己互相矛盾 → 用户读到错的信息

**所以"仓库里有" ≠ "用户能拿到" ≠ "用户能用到"。** 本 ref 的核心就是把这三件事拆开,要求每一步都用证据链验证。

## 2. 闸口一:用户视角审视(动手前必过)

每个改动动手前,先回答三个问题。**任一答"否"就该停手重判**:

### Q1:谁会用到?(受众清单)

| 受众 | 怎么识别 | 不为谁服务的常见误判 |
|---|---|---|
| **PyPI 用户**(`uv tool install sql-harness`) | `unzip -l dist/*.whl` 里的文件;`init` / `skill install` 的复制路径 | "文档里有" ≠ "用户能拿到" |
| **仓库贡献者**(读 git 源码) | 在仓库内任意路径 | 仓库内可见 ≠ 用户可见 |
| **Agent 运行时**(被 `apply_skill` 加载或 heredoc 注入) | `agent_loader.py` / `manager.py` / loader 注册表 | 写好了不挂上 loader = 死代码 |

### Q2:用户能完整走通吗?(UX 链路无断裂)

不是"功能实现了"就行,要**完整跑一次从装到用**:

1. **安装** → wheel 装到 venv
2. **初始化** → `sql-harness init` 写 `connections.toml`、拷 meta skills
3. **配置** → `add` 一个 DSN
4. **首次使用** → heredoc 进 run.py,helpers 自动注入
5. **进阶用法** → 自己写 hook / save 脚本 / run 重跑

每一环都必须有**代码路径支撑**,不能"用户应该会找到"。A01 §2.4 的 `agent-workspace/` 家规就是这个思路:仓库里的副本是"代码即文档",但 live copy 在 `$BH_SQL_HOME` —— 两者职责明确,不能混。

### Q3:必要性证据(为什么是现在加?)

如果只是"看起来有用"、"代码上能加"、"别人有我也想要",**默认不做**。必要性证据至少要满足一条:

- [ ] 有真实工作流卡在当前能力上(具体场景描述)
- [ ] 有 ≥3 个用户的相似需求
- [ ] 是基础设施(为后续 N 个功能铺路)
- [ ] 是安全 / 合规必须项

任一空白 → 不加。

## 3. 闸口二:孤儿清零(动手后 / 定期巡检)

### 3.1 什么是孤儿

满足以下**任一组合**的文件 = 孤儿:

| 信号 | 检测方法 |
|---|---|
| 全仓 0 引用(代码/文档/测试/SKILL/README) | `grep -rn <name> src/ tests/ SKILL.md *.md` |
| 不在 wheel 里 + 不在 init 复制列表 + 不在 skill install 复制列表 | `unzip -l dist/*.whl` + 读 `cli.py:cmd_init` / `cmd_skill_install` |
| loader 不识别该文件名 | 读对应 `*_loader.py` |
| 文档契约引用它(SKILL.md / README.md 提到)但代码不实现 | grep 反向 |
| 代码实现它但任何文档不引用 | grep 反向 |

**"仓库里有但任何路径都走不到"= 孤儿**,零容忍。

### 3.2 孤儿的处置(优先级排序)

按"动得最少"原则:

1. **删**(首选)—— 真没用的,直接删,任何改动都是噪音
2. **改 README 引用** —— 文档提到了但实现没有,要么补实现,要么改文档不依赖
3. **搬到对的位置** —— 受众错位(比如仓库内教学示例被当成运行时产物)
4. **挂上 loader** —— 实现了但没接入,补上注册路径
5. **加进 wheel** —— 真有用户价值但漏了 force-include,补 `pyproject.toml`
6. **降级为 example** —— 教学价值保留但明确标 "示例,不进入运行时"

**反模式**:把孤儿"挪到另一个不显眼的位置" / "加个 README 说明它的存在意义" / "重构得看起来有用" —— 都是给孤儿续命,不是清零。

### 3.3 巡检触发

- **每次 PR 前** —— 本次改动是否引入新孤儿?是否清掉旧的?
- **每季度 / 每次大版本前** —— 全量扫(grep `force-include` 路径 vs `grep -rn` 引用 vs `unzip -l`)
- **任何 "仓库里看起来有但用户报找不到"** —— 立即查这条链路

## 4. 实战模板:6 步判定

把两道闸口合起来,任何改动过这张表:

步骤 1 — **描述改动**:一句话说清"加什么 / 改什么 / 删什么"
步骤 2 — **闸口一 Q1**:谁会用到?能列出吗?
步骤 3 — **闸口一 Q2**:用户能完整跑通吗?写一遍 UX 链路
步骤 4 — **闸口一 Q3**:必要性证据满足至少一条吗?
步骤 5 — **闸口二**:**改动完之后**,新建的文件是否有引用?删除的文件是否还有引用?
步骤 6 — **过 A01 §3 速查表**:改动落在对的目录了吗?

**任一步答不出 → 停手,补证据再继续**。

## 5. 真实案例(skill 沉淀来源)

> 以下案例来自本 ref 沉淀前的对话,作为"为什么需要这道闸口"的实证。

### 案例:`agent-workspace/agent_helpers.example.py`

**质疑**:"用户装完 sql-harness 能看到这个文件吗?"

**证据链**(全部已核对):

1. `pyproject.toml:51-61` force-include 只列了 SKILL.md / interaction-skills / zones-meta-skills / web 资源 —— **不含 example.py**
2. `unzip -l dist/sql_harness-0.3.7-py3-none-any.whl | grep agent_helpers` 只命中 `agent_loader.py`(loader 本体)+ `helpers.py`(源码),**没有 example**
3. `cli.py:534 cmd_init` 全文 25 行,只写 `connections.toml` + 拷 `zones/meta/skills/*.md` —— **不复制 example**
4. `cli.py:470 cmd_skill_install` 从 `sql_harness/_skills/`(wheel 内)拷 SKILL.md / interaction-skills / agent-workspace-skills —— **不涉及 example**
5. `src/sql_harness/agent_loader.py:32-34` 明确 `if path is None or not path.is_file(): return 0` —— **loader 找的是 `agent_helpers.py`,不是 example**
6. 全仓 grep `agent_helpers.example` → **0 命中**
7. 仓库内唯二引用在 `agent-workspace/README.md:15-17`(列出 seed_users 等函数清单)

**判定**:

- 闸口一 Q1:PyPI 用户**拿不到**(证据 1-5),只仓库贡献者**看得见**——受众严重错位
- 闸口一 Q2:用户不能完整走通,因为文件压根不在用户机器
- 闸口二:README 引用是**孤儿引用**的唯一支撑 —— 删 example 必须同步改 README

**处置**:**删 + 改 README** 两步走(已落地,2026-09-27)。不是"挪到 zones/example_pg/"(语义错位,撞 per-zone hook 命名);不是"加 README 说明它的意义"(给孤儿续命)。

---

### 反面教材:如果当时没问闸口会怎样?

如果不审视,默认保留 → 仓库继续堆积"教学示例"——任何新贡献者来读都会困惑"这个文件是给谁用的?",要么误以为用户能用,要么直接删但漏改 README 形成新的不一致。**孤儿 = 隐性技术债,每加一个就稀释一次仓库的信号强度**。

## 7. 文档腐蚀的早期信号(项目价值预警)

> 单文件审视解决"该不该删这个文件",本节解决"整个 skill / 整个仓库的文档是不是在腐坏"。

### 7.1 早期信号清单(任一出现 = 立即巡检)

| # | 信号 | 检测方法 | 严重度 |
|---|---|---|---|
| 1 | **入口空转** —— 触发条件表里的信号没人触发,或触发后 ref 答非所问 | 看最近 N 个会话,有多少次真正进入 ref | 🟡 预警 |
| 2 | **ref 没人读** —— ref 存在但从未被加载 | 加埋点或看 git blame(长期无人动 = 无效 ref) | 🟡 预警 |
| 3 | **文档互相矛盾** —— A ref 说"放 X 目录",C ref 说"放 Y 目录" | 全仓 grep 同一概念的不同表述 | 🔴 立即修 |
| 4 | **重复内容** —— 多个 ref 说同一件事,但各自不完全 | 章节级相似度对比 | 🔴 立即合并 |
| 5 | **路径 / 类名 / 命令已过时** —— 文档说"调 X 函数",代码里 X 已改名 | 文档里的 `path:` `function:` `class:` 跟实际 diff | 🔴 立即修 |
| 6 | **空 ref** —— ref 文档存在但内容只剩标题 | 看文件行数 + 章节密度 | 🔴 立即删或填 |
| 7 | **膨胀失控** —— 主 SKILL.md 行数 > 200,ref 总数 > 10 但入口还是同一个 | 看主文档 + ref 总数 | 🟡 触发序列化 |
| 8 | **用户反复问同一问题** —— "怎么加 driver 啊" 一个月内问 3 次 | 用户信号 / 对话历史 | 🔴 ref 写得不够好,要重写 |

### 7.2 巡检节奏

- **每次 PR 前**:自查(本 PR 是否引入信号 3-6)
- **每季度 / 每次大版本前**:全量巡检(信号 1-8 全部过一遍)
- **任何"用户报找不到"**:立即查这条链路(信号 3/5)

### 7.3 处置原则(腐坏比空更糟)

| 信号 | 默认动作 |
|---|---|
| 入口空转 / ref 没人读 | 先**合并**到现有 ref,再考虑删;不要为"减少孤儿"而删有边缘价值的 ref |
| 文档互相矛盾 | 找出**最近改的那份**,以它为准回滚旧的 + 加信号 3 巡检 |
| 路径 / 类名过时 | 走 key_board 的 A03 内容同步,直接同步事实层 |
| 膨胀失控 | 走 A01 沉淀为 ref(本 skill 的本职),不是删 ref |
| 用户反复问 | 重写 ref(可能位置错、语气错、触发条件没命中) |

**核心原则**:**腐坏的 ref 比没 ref 更糟糕** —— 因为用户会去读它,读到错误信息后做错事。所以一旦发现腐坏,**优先删/合并/重写,而不是"先留着以后再说"**。

---

## 8. 何时**不**触发本 ref

- 紧急 hotfix(用户立刻受影响,先修后审视)—— 但修完补一次闸口回顾
- 安全漏洞(必须立即处理)—— 同上
- 纯文档 typo / 拼写 —— 不算改动,直接改
- 依赖升级 / 锁文件更新 —— 不引入新代码,跳过
